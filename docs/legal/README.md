# 법률 검토 자료 (2026-10-01)

직접 계약 구조(Clipers가 광고주·크리에이터 각각과 계약)로 가기로 정했다. 근거와 판례는 `docs/superpowers/specs/2026-10-01-creator-payouts-design.md` 4절.

| 문서 | 상태 |
|---|---|
| [terms-draft.md](terms-draft.md) | 이용약관 초안. 법률 검토 전, 게시 금지 |
| [privacy-draft.md](privacy-draft.md) | 개인정보 처리방침 초안. 법률 검토 전, 게시 금지 |

앱의 `/terms`, `/privacy`는 지금 "준비 중" 페이지다. 그런데 온보딩에서 두 문서에 필수 동의를 받고 있다. 검토를 마친 문서를 게시하기 전까지 이 상태는 출시를 막는 문제다.

## 1. 변호사에게 물을 것
1. 직접 계약 구조(약관 제3조)로 운영하면 전자지급결제대행업 등록 없이 가능한가. 현행법(~2026-12-16)과 개정법(2026-12-17~) 각각.
2. 광고주의 미사용 선급금을 반환(약관 제11조 제3항)해도 1번 판단에 영향이 없는가, 아니면 다음 캠페인 크레딧으로만 처리해야 하는가.
3. 크리에이터가 만 19세 미만일 때의 계약·지급 방법(법정대리인 동의 절차).
4. 광고 표시 의무(약관 제14조)를 어긴 크리에이터의 게시물에 대해 회사와 광고주가 지는 책임과, 약관으로 줄일 수 있는 범위.
5. 관할 법원 조항(약관 제25조)과 면책 조항(제23조)이 약관규제법상 유효한가.
6. 공개 캠페인 페이지에 크리에이터별 정산 금액(리더보드)을 공개해도 되는가. 동의가 필요한가.

## 2. 세무사에게 물을 것
1. 크리에이터 용역 대금을 사업소득(업종코드 940306)으로 3.3% 원천징수하는 것이 맞는가.
2. 소액부징수를 지급 1건 단위로 판단하는 것이 맞는가.
3. 광고주 서비스 대금의 부가가치세 처리와 세금계산서 발행 시점(선급 입금 시 vs 서비스 제공 시).
4. 사업자등록이 있는 크리에이터의 처리 방식.

## 3. 직접 계약 구조와 어긋나는 화면 문구
**2026-10-01 반영**: 아래 표에서 '환불' 행과 `campaign_escrow` 이름을 뺀 나머지를 고쳤다. 크리에이터에게는 '예산'이 아니라 '캠페인 지급 한도'로 말한다. 광고주에게 하는 "검증된 조회수만큼만 예산이 쓰여요", 브랜드 화면의 '남은 예산'은 광고주 자신의 서비스 대금이므로 그대로 둔다.

Clipers가 광고주 돈을 맡아 나눠 주는 중개자로 읽히는 문구들이다.

| 위치 | 지금 문구 | 방향 |
|---|---|---|
| `apps/site/app/page.tsx` 클리핑 설명 | 캠페인은 브랜드나 아티스트, 크리에이터가 예산을 걸고 여는 … 예산을 나눠 받고, 예산이 다 쓰이면 캠페인이 끝나요 | Clipers가 조회수만큼 지급하고, 캠페인 지급 한도에 도달하면 끝난다 |
| `apps/site/app/layout.tsx` 메타 설명 | 브랜드는 예산을 걸고 … 정산되는 | 같은 방향 |
| `apps/site/app/llms.txt/route.ts` | 예산을 걸고 여는 … | 같은 방향 |
| `apps/site/lib/creator-faq.ts` (budget-runs-out) | 크리에이터들이 캠페인 예산을 나눠 받기 때문에 | 캠페인마다 지급 한도가 있어서 |
| `apps/site/lib/guides/topic.ts`, `advertiser-problem.ts` | 예산을 나눠 받는 | 같은 방향 |
| `apps/site/lib/advertiser-faq.ts`, `guides/advertiser-problem.ts` | 쓰지 않은 예산을 환불받거나 | 변호사 답(1-2번)에 따라 "남은 서비스 대금 반환" 또는 "다음 캠페인에 사용" |
| 사이트·앱의 '남은 예산' 표시 | 광고주 예산 기준 | 크리에이터에게는 '남은 지급 한도'(크리에이터 단가 기준) |
| DB 이름 `campaign_escrow` | 에스크로 | 내부 이름이라 급하지 않음. 화면에 노출되면 '입금 확인'으로 |

## 4. 데이터 노출 (2026-10-01 실제 DB에서 확인)
**진행 상황**: 1단계(`supabase/migrations/20261001123839_campaign_finances.sql` — 브랜드·운영자용 `campaign_finances` 뷰, 공개용 `campaign_payout_limits()`)는 적용했고, 사이트·앱·주간 정산 코드는 이 경로를 쓰도록 바꿨다. **2단계(`supabase/pending/close_public_columns.sql`, 아래 1·2·4번 권한 회수)는 새 코드를 배포한 뒤에 적용한다.** 먼저 적용하면 배포된 옛 코드가 캠페인 데이터를 못 읽는다. 2단계는 트랜잭션 안에서 미리 돌려 역할별 결과를 확인했다(anon은 단가·예산·온보딩 답변 차단, 사이트 조회는 정상, 크리에이터는 예산 조회 불가, 브랜드는 자기 캠페인만, 운영자·서비스 키는 전체).
로그인하지 않은 사람(anon)이 API로 직접 읽을 수 있는 것들이다. 화면에 보이지 않아도 공개 키로 누구나 조회할 수 있다.

1. **`campaigns.brand_cpm`, `campaigns.total_budget`**: 공개 캠페인의 브랜드 단가와 총예산. 브랜드 단가는 비공개 원칙이고, 직접 계약 구조에서는 회사 마진이 드러난다. 사이트가 '남은 예산'을 계산하려고 읽는다(`apps/site/lib/campaigns.ts`). → 서버에서 계산한 크리에이터용 수치(남은 지급 한도)만 내보내는 함수로 바꾸고 anon 권한을 회수한다.
2. **`profiles.interests`, `on_camera`, `experience_level`, `terms_agreed_at` 등**: 공개 캠페인에 참여한 크리에이터와 브랜드의 온보딩 답변. 사이트는 `display_name`만 쓴다. → anon 칸 권한을 `id`, `display_name`, `role`로 줄인다.
3. **`settlements.amount`(크리에이터별 정산액)**: 리더보드에 쓰인다. 공개 여부를 1-6번 질문과 함께 정하고 처리방침에 적는다.
4. **`clips.rejection_reason`, `reviewed_by`, `escalation_*`**: 승인된 클립만 공개라서 반려 사유는 보통 비어 있지만, 쓰지 않는 칸은 권한을 회수한다.
